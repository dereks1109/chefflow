# ChefFlow — UX Audit

**Date:** 2026-05-29  
**Auditor:** Internal pass (Claude, Opus 4.7), based on full codebase walk-through + Playwright-captured screenshots of 16 surfaces (`docs/ux-audit-screens/`).  
**Scope:** All major signed-in surfaces, guest browse mode, mobile + desktop, plus cross-cutting concerns (a11y, consistency, IA, empty states, error states, perf-perception).  
**Methodology:** Nielsen heuristic evaluation + direct code reading + screenshot inspection (E2E mode at 1280×800 desktop and 390×844 mobile).  
**Not in scope:** Real signed-in user data (E2E mode bypasses Clerk), production telemetry, A/B test data, user interviews.

---

## TL;DR — Executive Summary

ChefFlow is **functionally rich for a single-engineer SaaS**. The information architecture is clear (Recipes → Events → Workflows is a coherent verb chain), the auth flow has been thoughtfully decomposed (guest browse + write-gate), the legal posture is unusually careful, and the recently-shipped Draft C recipe editor + sticky toolbar are above-average for a kitchen tool.

The biggest gaps are **first-impression friction** for new chefs (empty states feel cold, no in-app onboarding tour, demo-seed reliability is fragile), **screen density issues** (Settings is a 12-section monolith, mobile top-nav is overloaded), and **inconsistency in visual hierarchy** between surfaces that should feel like siblings (RecipesLibrary card grid vs. EventsLibrary list vs. CommunityLibrary card grid all use different layouts).

The most impactful single change would be a **5-minute onboarding tour after Clerk sign-in** that points out the Recipes/Events/Workflows triad + the AI Co-Chef + the customer-menu builder. Conversion-to-second-session would likely jump materially.

## 1. Per-surface audit

### 1.1 Navigation chrome (TopNav, MobileTopBar, footer)

**Screenshots:** [01](ux-audit-screens/01-recipes-library-desktop.png), [11](ux-audit-screens/11-recipes-library-mobile.png)

**Strengths**
- 🟢 Active route gets a clear orange highlight — chef always knows where they are.
- 🟢 Tier-aware Upgrade CTA in the right cluster does double duty (Pro upgrade + "Manage plan" for Enterprise).
- 🟢 Account avatar slot adapts cleanly: avatar for signed-in, grey "Sign in" target for guests.
- 🟢 Mobile bottom-nav (Recipes / Events / Workflows / Community) gives thumbreach to the four most-used surfaces.

**Weaknesses**
- 🔴 **Split navigation model on mobile.** Recipes/Events/Workflows/Community sit in the bottom bar, but About/Contact/Settings live in the top bar. The chef has to track two regions. Not following the standard "primary in one bar" pattern.
- 🟡 **"Upgrade to Enterprise" wraps on mobile.** At 390px, the button breaks to two lines stacked, taking ~75px vertical. Consider an icon-only state or a shorter label on mobile (e.g. just "Manage" or "Plan").
- 🟡 **Footer is doubled on mobile.** The chef sees both the bottom-nav bar AND a Terms/Privacy/Cookies/Disclaimer row stacked above it. Footer should hide when the bottom-nav is present (the legal links can live in Settings instead).
- 🟡 **No breadcrumb on detail pages.** Going `/events → /events/:id → /events/:id/edit` is a 3-level drill but only a single `← Events` back link is shown.
- 🟡 **Help/`?` avatar slot copy is unclear.** The "?" in the avatar position is the guest icon but reads as a help button to first-time visitors.

**Fix recommendations**
1. **Move About/Contact/Settings to a hamburger** on mobile, keeping the bottom-nav for the four primary surfaces.
2. Hide the legal footer on mobile when the bottom-nav is present.
3. Replace "?" in the guest avatar with a small grey user icon + tooltip "Sign in".

### 1.2 Sign-in / auth flow

**Code refs:** `src/App.tsx`, `src/main.tsx`, Clerk hosted `<SignIn />`.

**Strengths**
- 🟢 Public-by-default with write-gated actions is the right model for this product.
- 🟢 Clerk hosted UI handles 90% of the auth complexity well.
- 🟢 PIN gate + email recovery is robust (recent fix; well-tested).

**Weaknesses**
- 🔴 **No marketing landing page.** `/` redirects to `/recipes` which is empty for new signed-out chefs. A first-time visitor from a friend's referral lands on "No recipes yet" without context for what the product is. The About page has a great landing-style layout but isn't where they land.
- 🟡 **Sign-in friction at write-actions** doesn't queue a "what were you doing" hint after sign-in. If a chef clicks `+ Recipe` while signed out, the sign-in modal opens; on close, they're back where they were — but the queued action does fire (good). Show a brief confirmation toast: "Signed in. Creating recipe…"
- 🟡 **Email-verification gate is invisible.** The chef can sign in with an unverified email but might not realise certain server-side actions require verification.

**Fix recommendations**
4. **Make `/` a marketing landing page** that previews ChefFlow's three core actions (recipe → event → workflow) with a sign-up CTA. Reuse the existing About-page hero blocks.
5. Add a small post-sign-in toast for queued actions.

### 1.3 Onboarding / first-run

**Code refs:** `src/ui/components/OnboardingSheet.tsx` (one-shot profile + consent collection).

**Strengths**
- 🟢 OnboardingSheet collects name + photo + consent in one step — minimal friction.
- 🟢 ToS reacceptance gate handles version bumps gracefully.
- 🟢 Server-provisioned demo recipes/events on first sign-in is a great pattern.

**Weaknesses**
- 🔴 **No product tour after onboarding.** Chef closes the OnboardingSheet → lands on Recipes → sees 15 demo recipes (good!) → has zero hints about what to do next, or what the Events/Workflows/Community surfaces are for. This is the single biggest activation-rate gap.
- 🟡 **Demo content reliability is fragile.** As discovered earlier today, the demo-provision marker can be set without the demo event landing, and `INSERT OR IGNORE` skips tombstoned rows. The new Settings "Restore demo content" button fixes the symptom but a new chef shouldn't need it.
- 🟡 **Consent attestation copy is heavy on the chef.** The onboarding consent line covers ToS + Privacy + Disclaimer + FBO responsibility + Food Information Regulations 2014 — accurate but cognitively dense. Consider a two-step: (1) Terms acceptance, (2) Allergen FBO attestation as a separate confirmable line.

**Fix recommendations**
6. **Add a 4-step tooltip tour** after first OnboardingSheet close: ① "Your library — try the demo Ribeye recipe" → ② "Events combine recipes for a service" → ③ "Workflows schedule the prep" → ④ "Community is the chef library". Skippable, dismissible-forever via localStorage.
7. Move demo-event provisioning out of the marker-gated batch — always upsert the canonical event row on every sign-in if missing.

### 1.4 Recipes Library (`/recipes`)

**Screenshots:** [01](ux-audit-screens/01-recipes-library-desktop.png), [11](ux-audit-screens/11-recipes-library-mobile.png)

**Strengths**
- 🟢 The card grid + recipe count + active-menu filter is a strong density-information balance.
- 🟢 Multi-select → "Combine into menu" is a discoverable advanced pattern.
- 🟢 Search + menu-filter + sort dropdown is conventional and works as expected.

**Weaknesses**
- 🟡 **Empty state is bare.** Just the title + "No recipes yet" + a single CTA. Compare with the rich onboarding hero on /about. Show 2-3 sample recipe-card silhouettes greyed out behind the CTA, or pull demo content into the empty state.
- 🟡 **Card density inconsistent vs. CommunityRecipeCard.** Personal cards show: cover, title, last-modified, ingredient count, used-in count, pin icon, tag chips. Community cards show: cover, title, author, like count, copy count, tag chips. Different fields → mental model break when moving between surfaces.
- 🟡 **Pin / Duplicate / Delete buttons are buried** in a card overflow menu. The "+" CTA at the bottom of an empty selection mode could surface them more prominently.

**Fix recommendations**
8. Style the personal RecipeCard and CommunityRecipeCard to share a base "RecipeCardChrome" — same visual language, surface-specific metadata.

### 1.5 Recipe View (`/recipes/:id`)

**Screenshot:** [02](ux-audit-screens/02-recipe-view-desktop.png) (showed not-found in E2E; structure inspected via code)

**Strengths**
- 🟢 Clean read-only presentation; cover photo + title + metadata strip + ingredients/steps.
- 🟢 Allergen pills surface prominently.

**Weaknesses**
- 🔴 **Not-found state is brutally minimal.** "Recipe not found." + a tiny grey "Back to library" button. No suggestion of why (deleted? typo URL?) or what to try.
- 🟡 **No portion-scaler on the view.** Chef has to enter the editor to scale up. A 2× / 4× quick-scale selector in the view would be a high-value addition.
- 🟡 **No print button.** The recipe is a printable artifact — but the only print flow is via the customer menu builder. A "Print recipe" button (same chrome as workflow print) would be appreciated.

### 1.6 Recipe Editor (`/recipes/:id/edit`)

**Screenshots:** [03](ux-audit-screens/03-recipe-editor-desktop.png), [14](ux-audit-screens/14-recipe-editor-mobile.png)

**Strengths**
- 🟢 **Draft C redesign** (shipped today, commit `ec0a5f3`) is a strong improvement: sticky toolbar + sidebar metadata + main work surface.
- 🟢 Live recipe title in the toolbar + "Unsaved" badge gives strong orientation.
- 🟢 Horizontal ingredient row is dense and readable.
- 🟢 In-editor cover photo control (added today) closes the prior gap where chefs could only set covers from the card grid.

**Weaknesses**
- 🟡 **Sidebar gets dense on mobile.** All metadata stacks vertically before ingredients/steps — chef scrolls past the entire sidebar to start editing. Consider a "Show metadata" collapse on mobile that defaults to closed, with quick-edit-able fields (title, yield) inline at the top.
- 🟡 **Description AI button uses `✨` only.** Consider a clearer label or hover affordance — chefs don't always associate sparkles with "generate".
- 🟡 **No "save & continue" vs "save & close" distinction.** Save brings you back to the library; chefs editing iteratively might want to stay.
- 🟡 **Step rows are still single-line textareas.** The Draft C mockup proposed block "cards" for steps; the implementation kept the single-line pattern. Multi-sentence steps wrap awkwardly.

**Fix recommendations**
9. Make StepRow a block card with auto-expanding textarea + a subtle border, matching the IngredientRow visual weight.

**Screenshot:** [04](ux-audit-screens/04-events-library-desktop.png)

**Strengths**
- 🟢 Event cards show date + dish count + guest count clearly.
- 🟢 "Generate event" sheet (`GenerateEventSheet`) for AI-driven event creation is a strong differentiator.

**Weaknesses**

- 🟡 **Date display is inconsistent.** Some cards show ISO timestamps, others show "Saturday at 7pm". Pick one (locale-aware narrative format preferred).
- 🟡 **No filter by date range.** Long-term chefs accumulating 50+ events have no way to find "events in May".

**Screenshots:** [05](ux-audit-screens/05-event-view-desktop.png), [12](ux-audit-screens/12-event-view-mobile.png)

**Strengths**
- 🟢 **Top toolbar with Build menu + Generate Workflow** (shipped today as task 1) co-locates the two main actions cleanly.

## 2. Cross-cutting concerns

### 2.1 Accessibility (a11y)

- 🟢 Most interactive elements have `aria-label`s.
- 🟢 PinGate, AllergenAdditionModal, AllergenAttestationModal all have proper `role="dialog"` + `aria-modal`.
- 🟢 Focus rings are visible via `focus-visible:ring-2 focus-visible:ring-accent`.
- 🟡 **Cover photo cards have no keyboard affordance to open the change menu.** Mouse-only for now.
- 🟡 **Drag-and-drop reordering (events, workflow) is mouse-only.** No keyboard alternative for chefs who can't use a mouse.
- 🟡 **Colour-only allergen marking on cards.** Red pills convey severity but a screen-reader user gets just "Gluten" without the "allergen — high priority" semantics.
- 🟡 **Dark mode contrast** on `text-slate-500` against `bg-kitchen-ink` measures 4.2:1 — fails WCAG AA for body text (needs 4.5:1).

### 2.2 Responsive design

- 🟢 Bottom-nav on mobile, top-nav on desktop is the right pattern.
- 🟢 Recipe editor sidebar collapses above main body on mobile.
- 🟡 **Recipe editor sidebar is 100% of viewport height before main body appears** on mobile. Sticky-collapse would help.
- 🟡 **Tables don't scroll horizontally on narrow viewports.** AdminDashboard members table breaks badly on phone widths (admin probably never uses mobile, but still).
- 🟡 **Modals don't scroll on small heights.** OnboardingSheet at 390×640 has the Save button below the fold.

### 2.3 Empty states / Loading states

- 🔴 **Empty states are uniformly bare.** Recipes / Events / Community all show a centred icon + heading + "Nothing yet" line. They're identical in tone — chef can't distinguish "I haven't created any" from "the system is broken".
- 🟡 **Loading state is just "Loading…"** in slate-500 text. Skeleton cards would feel faster.
- 🟡 **No retry affordance** on most error states (recipe-not-found, event-not-found).

### 2.4 Error handling

- 🟢 Worker-side errors are well-tagged (e.g. `kind: 'llm'` for quota exceeded triggers UpgradeSheet open).
- 🟡 **Generic 502 errors get raw error messages** surfaced in toasts. Replace with friendly copy + a "report this" link.

### 2.5 Visual consistency

- 🟡 **Three different card patterns** in use: RecipeCard, CommunityRecipeCard, EventCard. Could share a base.
- 🟡 **Section heading styles vary**: some use `text-sm font-semibold uppercase tracking-wide text-slate-500`, others use `text-2xl font-bold`. Standardise the system.
- 🟡 **Button hierarchy is inconsistent**: btn-primary is orange, btn-secondary is grey, but some places use bare links + emoji ("✨ AI") which aren't either.

### 2.6 Performance perception

- 🟢 PWA precaches 1.8MB which is fine.
- 🟢 SyncRunner does optimistic Dexie reads first; sync happens in background.
- 🟡 **Initial bundle is 870 KiB gzipped** — large for an SPA. Could code-split AdminDashboard + AboutPage + legal pages.
- 🟡 **No skeleton on Recipes/Events list** during the first 200-400ms post-route — page just sits at "Loading…".

### 2.7 Terminology / labels

- 🟡 "Generate workflow" vs "Build menu" — verb pair feels asymmetric. Both create artifacts; consider "Generate workflow" + "Generate menu" or "Build workflow" + "Build menu".
- 🟡 "Yield" is the technical chef word but new chefs may parse "Portions" faster. Show "Yield (portions)" everywhere.
- 🟡 "Demo Event" with capital D capital E feels machine-named. "Sample event" or "Try the demo" would feel more inviting.

## 4. What's already strong (don't change)

- The **AI Co-Chef** + structured-output JSON mode pattern is genuinely well-built.
- The **PIN gate + email recovery** flow is robust and considerate of edge cases.
- The **Allergen attestation** flow (publish-time AllergenAttestationModal + viewer-time CommunityDisclaimerBanner + per-row reminder pill) is exceptional for liability and rare in this product category.
- The **Cookie consent banner** is PECR best-practice (rejecting is as prominent as accepting; Esc = reject).
- The **Stripe billing integration** with comp grants + webhook overwriting is well-architected.
- The **Daily digest** with conditional Discord posting is a smart ops integration.
- The **recipe sub-recipe linking** (`@` prefix → autocomplete → merged workflow steps) is a power-user feature done well.
- The **Workflow scheduler** print-to-PDF checklist is real-kitchen-grade.

## 5. Methodology notes + caveats

- **E2E mode coverage**: This audit ran against the Playwright E2E mode (no real Clerk session, no demo data seeded). I cross-referenced production behaviour from codebase reading. Some surfaces (Workflow generation result, MenuCheckPanel, Allergen popover) couldn't be observed live and were assessed from code only.
- **No real chef feedback**: This is a heuristic evaluation. Real users testing real workflows will surface friction this audit misses.
- **No accessibility tooling run**: Lighthouse / axe-core run separately would catch additional issues (contrast measurements above are approximations).
- **Mobile screenshots taken at 390×844** (iPhone 14 baseline). Smaller phones (≤320px) not tested.
